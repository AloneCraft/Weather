# QA_WORKFLOW

品質改善を、途中停止・再開できる方式で進めるための運用ルール。
実作業は、ユーザーが次に指定するゴールから開始する。このファイルは運用ルールの正本であり、実行状況の記録は `qa/` に置く。

## 0. このリポジトリでの前提

### 0.1 読み替え

運用ルールの原文は特定のゲームエンジンを想定した表現を含む。このリポジトリは .NET MAUI(Android / iOS)+ SkiaSharp のアプリで、Unity は使っていない。以下のように読み替える。

| 原文 | このリポジトリでは |
|---|---|
| Unity、OS、描画API等の対象環境 | .NET SDK(`global.json`)、MAUI ワークロード版、OS、SkiaSharp の描画経路(Android: SKGLView / iOS: SKMetalView / テスト: オフスクリーン) |
| Editor操作・Player実行手段 | `dotnet build` / `dotnet test`、CI(GitHub Actions)、Android エミュレーター・実機、iOS シミュレーター |
| Unityのシーン・アセット・設定・.meta | `.csproj`・`Directory.*.props`・`global.json`・XAML・リソース・ゴールデン画像・記録データ(`tests/Weather.Providers.Tests/Fixtures/`)・生成データ(`src/Weather.Geo/Data/*.bin`、`*.Table.cs`)。コードと同じ扱いにする |
| 同じUnityプロジェクトを並列使用しない | 同じソリューション(同じ `bin/` `obj/`)への `dotnet build` / `dotnet test` を並列実行しない。エミュレーターも同時に1つのテストだけが使う |
| 目視確認 | 描画の見た目、操作感、エミュレーター・実機での確認(`docs/Design/TestStrategy.md`「エミュレーターでの確認手順」) |

### 0.2 既存の規約・記録との関係

- 作業規約は `AGENTS.md` と `AI_SYNTAX_RULES.md` に従う。C# を修正するときは `AI_SYNTAX_RULES.md` の書式(詰めた空白、`this.` など)に合わせる。
- テストの層・不変条件の対応表・CI の構成は `docs/Design/TestStrategy.md` が正本。このファイルに複製しない。
- Test ID は次の形式にする(新しい体系を作らない)。
  - 自動テスト: `{テストプロジェクト}/{クラス}.{メソッド}`(例: `Weather.Providers.Tests/WeatherProviderRouter.RouteForecast`)
  - 手動回帰: `MAN-ANDROID-n`(`TestStrategy.md`「エミュレーターでの確認手順」の手順 n)。新しい手動回帰は `MAN-{領域}-n` で追加する。
- `TestStrategy.md`「不変条件をテストへ移す対応表」の不変条件(日本域は気象庁のみ、全データに出典、MET をバックグラウンドで取得しない、など)は、修正で破ってはならない前提として扱う。防御コードや出典表示を、テストを通すために削除・緩和しない。
- 運用開始前の QA 記録は存在しなかった(2026-10-04 に確認)。したがって `qa/` は新規作成であり、重複する記録はない。
- ユーザーへの説明・記録の文章は日本語にする(`AGENTS.md`)。
- 運用中の確認事項は `qa/handoff.md` に集約する(最大5件)。会話で質問するときは `AGENTS.md` の「質問は1つずつ」に従う。

### 0.3 実行環境の制約(記録で必ず区別する)

- クラウドセッションのコンテナには `dotnet` が入っていない場合がある。その場合、自動テストは `NOT_RUN`(理由: 環境)として記録し、PASS 扱いにしない。ツールの導入は、実行枠の開始時にユーザーの指示または許可された変更範囲に含まれる場合だけ行い、導入した事実と版を記録する。
- ゴールデン画像は Windows で生成・比較する(`TestStrategy.md`)。Windows 以外の結果は、ゴールデン画像の PASS / FAIL の証拠にしない。
- CI(`.github/workflows/ci.yml`)は `main` と `feature/**` への push、および Pull Request で動く。他のブランチへの push では動かない。CI の結果を証拠にするには、対象コミットで実際に実行されたジョブの結果だけを使う。Pull Request の作成は、ユーザーの明示指示があるときだけ行う。
- コンテナは使い捨てである。記録を再開に使うには、`qa/` の変更をコミットして保存する必要がある。
- push の許可(ユーザー指示、2026-10-04): クラウドで作業を開始するたびに、そのセッション専用のブランチを使う場合に限り、そのブランチへの push は許可されている。
  - 許可の範囲は、そのセッション専用のブランチ(セッションが指定した `claude/…`)だけ。`main`、他のセッションのブランチ、既存の `feature/**` へは push しない。
  - 新しいクラウドセッションでは、前のセッションのブランチを使い回さず、新しいブランチで始める。
  - Pull Request の作成、公開、申請は、この許可に含まれない。ユーザーの明示指示があるときだけ行う。
  - 履歴の書き換え(force push など)は許可に含まれない。

### 0.4 ファイル配置

| パス | 内容 | git |
|---|---|---|
| `docs/QA_WORKFLOW.md` | この運用ルール | 追跡 |
| `qa/state.json` | 実行枠、キュー、各問題の状態、依存関係、再試行条件 | 追跡 |
| `qa/history.jsonl` | 追記式の履歴 | 追跡 |

`docs/` と `qa/` はどの `.csproj` からも参照されず、リリース成果物(AAB)にも含まれない。出荷物に開発記録を混入させる変更(`.csproj` からの参照、リソースへの追加)は行わない。

## 目的

限られた実行時間で、重要な不具合を減らし、
いつ中断しても、確認できた状態と残課題を区別して再開できるようにする。

「すべて直るまで同じ問題を無制限に繰り返す」のではなく、
優先する問題を選ぶ
→ 証拠を取る
→ 限定した修正を試す
→ 検証する
→ 修正確定／保留／人間確認待ちを記録する
→ 次の問題を選び直す
という小さな単位で進める。

ここでの1単位は「必ず1件直すこと」ではない。
「1件に対する試行と、その結果の保存」までである。

## 1. 初期設定

以下は実績に基づく最適値ではなく、変更可能な初期予算とする。変更はユーザーの明示指示で行い、`qa/state.json` の `budget` に反映する。

- 通常モード: FOCUSED
- 1回の実行枠: 最大4時間
- 1件への修正試行: 原則1回
- 新しい証拠や明確な進展がある場合のみ、同じ実行枠で2回目を許可
- 1件の調査・修正・関連確認: 原則合計30分以内
- 探索的テスト: 実行枠全体で合計30分以内
- 終了整理のために最後の15分を確保
- 未検証の修正を同時に抱える件数: 1件まで
- テスト統合: 候補整理のみ

長いビルドなどで個別予算を超える必要がある場合は、短く切れない理由と必要な確認を記録し、無理に途中結果を合格扱いしない。
予算を消化するためだけの待機や、同じ結果しか得られない繰り返しは行わない。

## 2. 記録を正本にする

既存の記録方式を優先し、不足する場合のみ次を用意する。

- `QA_WORKFLOW.md`: この運用ルール。
- `qa/state.json`: 実行枠、作業キュー、各問題の状態、依存関係、再試行条件。
- `qa/history.jsonl`: テスト、探索、修正試行の追記式履歴。
- `qa/handoff.md`: 人間向けの短い現状説明、確認事項、次の作業。

詳細ログ・画像・差分は別の成果物として保存し、履歴から参照する。
出荷パッケージへ不要な開発記録を混入させない。

最初に記録するもの:

- 実行枠のID
- 開始時刻と終了期限
- 対象コミット
- 未コミット変更を識別できる差分またはハッシュ
- .NET SDK・ワークロード・OS・描画経路等の対象環境
- 今回のリリース対応範囲
- 許可された変更範囲
- 利用可能なテスト・ビルド・エミュレーター・実機の手段

コミットIDだけで未コミット変更まで識別したことにしない。

各問題には安定したBug IDを付け、次を記録する。

- 症状、再現条件、期待結果
- 重大度と修正優先度
- 原因の確定事項／仮説／不明
- 依存する問題、影響する問題
- 実施済みの試行、否定された仮説
- 関連Test ID
- 次に試せる条件
- 状態と証拠の保存先

状態は少なくとも以下を区別する。

- `READY`
- `IN_PROGRESS`
- `FIXED_UNVERIFIED`
- `VERIFIED`
- `NEEDS_HUMAN`
- `BLOCKED`
- `DEFERRED`

`VERIFIED` には検証したコード版・環境・方法を必ず紐付ける。
必須の目視確認が残るものは、`VERIFIED` にしない。

記録は各操作の前後に逐次保存する。
終了時だけまとめて保存する方式は禁止する。
状態ファイルの更新は、可能なら一時ファイルからの置換を使い、中途半端な内容で上書きされる危険を減らす(手順は 13.3)。
履歴は過去の失敗を消さず追記する。

## 3. 開始・再開時の処理

最初に `QA_WORKFLOW.md`、`state.json`、`handoff.md` を読む。
全履歴を毎回読み直さず、必要な問題の記録だけ追加で読む。
現在のGit差分、実行中プロセス、テスト結果と照合する。
記録と実際のコードが一致していると思い込まない。

前回 `IN_PROGRESS` だった作業があれば、新しい問題へ移る前に次を確認する。

- 編集はどこまで行われたか
- テストは未開始／実行中／終了のどれか
- 終了コードとログは残っているか
- 変更は採用済みか、検証待ちか
- `dotnet` / エミュレーター等がまだ同じソリューションを使用していないか

不明な結果は `UNKNOWN` または未検証として扱う。
同じテストやプロセスを重複起動しない。
ユーザーによる追加変更を見つけた場合は保護し、前回の差分を機械的に適用・復元しない。
再開しただけで予算・試行回数をリセットしない。
新しい実行枠の開始や予算追加は、ユーザーの明示指示で行う。

実行環境と基本機能の短いSmokeを確認し、その後、未処理キューを並べ直す。
毎回最初からFull Regressionをやり直さない。

## 4. 次に行う作業の選び方

「簡単なものだけ」でも「重大な一件に永久に固執」でもない。
依存関係と影響を優先し、その中で短時間に進展するものを選ぶ。

優先順位の基本:

1. 中断された未検証変更の復旧・切り分け
2. 他の検証を無効にする共通障害や重大な安全問題
3. 直近の変更で影響を受ける重要機能のテスト
4. 修正済み問題の再現テストと関連回帰
5. 重要度が高く、独立して修正・検証できる既知問題
6. 関連変更によって再確認する理由ができた保留問題
7. 履歴上の発見効率が良い回帰・探索
8. 低優先度の未実施テストや広い回帰

同程度の優先度では、次から順序を決める。

- 準備を含む実行時間
- 過去に見つけた独立した不具合の重大度
- 今回の差分との関連
- 他の問題を解消できる可能性
- 検証範囲の重複

記録が少なければ定性的に判断する。
実測していない発見確率や精密なスコアを捏造しない。
重要な必須テストを、「過去にずっとPASSしている」という理由だけで除外しない。

- FOCUSED: 上位の関連テスト・重要問題を中心に処理する。
- EXTENDED: 同じ優先順で進め、上位が片付いたら低優先度の既存テスト・広い回帰まで進む。

対応範囲外の新機能開発には拡大しない。
探索は既知問題の処理や必要な回帰を妨げない範囲で、操作の組合せ・状態遷移・テストの薄い部分を選ぶ。

## 5. 不具合1件に対する処理単位

修正する前に、次を記録する。

- Bug IDと試行番号
- 選んだ理由
- 修正前のコード状態
- 観測した事実
- 今回検証する原因仮説
- 変更予定の範囲
- 正しく直ったと判断する方法
- 採用しない場合の変更の隔離・復元方法

続いて:

1. 再現を確認する
2. 既存テストを使うか、最小の再現テストを追加する
3. 可能な限り修正前FAILを記録する
4. 根拠に基づく必要最小限の修正を行う
5. 再現テスト、関連回帰、必要な不変条件を確認する
6. 差分と証拠を保存する
7. 採用／検証待ち／保留を確定する

再現できない場合は、観測を改善する。
原因不明のままコードを書き換えない。
自動化困難な操作や描画の問題は、初期条件・操作手順・期待結果を持つ手動回帰として残す。
コードを読んだだけで実操作PASSにしない。

## 6. 直らなかったとき

1回目の試行で直らなければ、進展を判定する。

進展あり:

- 新しい実行ログが取れた
- 原因仮説を一つ否定できた
- 再現条件を絞れた
- 最初に不変条件が破れる場所を特定できた

これらに基づき次の試行が具体化し、予算が残る場合だけ2回目へ進む。

進展なし:

- 同じ仮説を言い換えただけ
- 同じ失敗を同じ環境で繰り返している
- 根拠のない数値調整や分岐追加になっている

この場合は保留し、独立した次の問題へ進む。
保留時には必ず、次を残す。

- 何を試したか
- 何が分かったか
- 何が分からないか
- 次に必要な証拠または人の判断
- 再試行可能になる条件

同じ未変更コード・同じ証拠しかない問題を、キューが一周したという理由だけで再試行しない。
重大な共通障害であっても無制限に試行しない。
それに依存する作業を `BLOCKED` とし、独立して検証可能な作業だけ続ける。

## 7. 未完成の修正を次へ持ち込まない

Aの修正が失敗したまま、同じ作業状態へBの修正を積まない。
Aの試行差分とログを保存し、作業前に戻せる場合は「今回自分が加えた変更だけ」を戻す。
または隔離された作業領域へ残す。
ユーザー変更を含む全体reset、clean、無差別なファイル復元は禁止。
安全に隔離・復元できない場合は、別の問題へ進まず、現在の状態を記録して停止する。

人間確認待ちの変更も同様に、承認前の前提として依存する修正を積まない。

テスト資産・設定・生成データ(0.1 の表)の変更もコード変更と同じように扱う。
同じソリューションに対するビルド・テストを並列実行しない。
独立性と実行環境が確認できない並列化は行わない。

## 8. 別の修正が保留問題に効いた可能性があるとき

Bの修正が採用されたら、Bと依存関係・状態・変換処理を共有する保留問題を確認する。
関連するものだけ、短い再現テストを再実行する。
毎回すべての保留問題を再実行しない。

Aの症状が消えた場合も、「Bを直したからAも根本解決」と即断しない。

- Aの元の再現条件
- 必要な境界条件
- 必要な関連回帰

を確認し、検証した版と証拠を記録する。
原因関係が未確定なら、そのまま未確定と残す。
新しい証拠が得られた場合のみ、Aを再試行可能なキューへ戻す。

## 9. 人間確認はまとめる

自動テストで判断できることを毎回ユーザーへ聞かない。
操作感、仕様の選択、目視しかできない描画、互換性を壊す方針変更は `NEEDS_HUMAN` へ送る。
その判断に依存しない作業は続けてよい。

人間向け確認は、重要なものを最大5件にまとめ、`qa/handoff.md` へ常に更新する。
各確認には以下を付ける。

- 質問IDと関連Bug ID
- 確認するコード版・画面・設定
- 具体的な操作手順
- 期待する見た目や挙動
- 利用可能なら比較画像・動画・ログ
- AIでは確定できなかった理由
- 選べる回答、または必要な観測
- 回答によって次の作業がどう変わるか

「動作確認してください」だけで終わらせない。
同じ判断に依存する問題は、質問をまとめる。
ユーザーの回答は判断記録として保存し、回答によって実際に確認できた範囲だけを更新する。
一つの目視確認を全テストのPASSへ拡大しない。

## 10. 安全停止と強制中断からの復旧

ユーザーから「安全停止」の指示を受けたら、新しい修正・探索・長時間テストを開始しない。
現在の小単位について、次のどれかを選ぶ。

- 検証して採用
- 差分を保存して隔離
- 未検証であることを明示して停止

時間が足りない場合は、検証を省いて採用しない。
`state`、`history`、`handoff` を更新し、起動したテストやプロセスが残っているかも記録する。

強制終了・クラッシュ等で最後の記録がない場合は、次回開始時に `IN_PROGRESS` の実態を調べて復旧する。
途中状態を推測で完了へ変更しない。
ユーザーがPCへ戻ったことを勝手に検知できると仮定しない。
停止指示が伝わった場合、または保存した期限に達した場合に処理する。

## 11. 統計

テスト実行ごとに、次を記録する。

- Test ID、実行種別、対象版、環境
- PASS / FAIL / ERROR / NOT_RUN
- 準備／実行／後処理の時間
- 関連Bug ID、証拠

修正試行ごとに、次を記録する。

- Bug ID、試行番号、仮説
- 調査／修正／検証時間
- 結果、採用した差分、再試行条件

探索ごとに、次を記録する。

- 目的、対象版、環境
- 実探索時間、操作要約、発見Bug ID

測定不能は「不明」、推定値は「推定」とする。
同じバグの再実行FAILを新規発見件数へ加算しない。
共有セットアップ時間を重複計上しない。
テストの統合はこの運用中に実装しない。準備処理の共有などの候補を記録するに留める(`state.json` の `consolidation_candidates`)。

## 12. 終了条件

次のいずれかで今回の実行枠を終了する。

- 今回対象の実行可能な作業を処理した
- 保存済みの時間・試行予算に達した
- ユーザーが安全停止を指示した
- 残りが人間判断待ち、依存障害、または新証拠待ちだけになった
- 安全に編集・検証を続けられなくなった

終了理由を満たすために、実行できる仕事を根拠なく保留へ移してはいけない。
終了時には、次を分ける。

- 実装済みか
- 必要なテストで検証済みか
- 目視確認待ちか
- 未解決か

短い関連テストが通ったことを、Full Regression全PASSやリリース準備完了とは扱わない。
最後に以下を会話にも出力する。

1. 今回の終了理由
2. 検証済みの改善
3. 未解決・検証待ち・保留とその理由
4. 次に再開する問題
5. 人間へ確認したい事項、最大5件
6. 実測した作業時間と残り予算
7. 現在のコード状態と未検証差分
8. 記録の保存先と、保存・読み取り確認の結果
9. 最終テストの対象版、実行結果、証拠

「実行枠を終了できた」と「製品品質が合格した」を区別する。
記録保存後は自動で新しい実行枠や全面再設計を開始しない。

## 禁止事項

- 合格させるためだけのテスト削除やassertion緩和
- 対応範囲内の重大バグの勝手なKnown Issue承認
- 必要な防御コードの機械的削除
- 根拠のないclamp、fallback、テスト専用分岐
- 同じ証拠での無制限再試行
- 未検証変更の積み重ね
- 無関係な整理、新機能追加、無断の大規模再設計
- 未実行、未保存、未計測の捏造
- ユーザーの変更破棄、無断の公開・申請・push(許可された push の範囲は 0.3)

## 13. 記録の書式と操作手順

大規模な管理ツールは作らない。標準の `git` / `jq` / `sha256sum` だけで扱える最小の書式にする。

### 13.1 `qa/state.json` の主なキー

| キー | 内容 |
|---|---|
| `schema_version` / `revision` / `updated_at` | 書式の版、更新ごとに +1 する通し番号、更新時刻(UTC) |
| `mode` / `budget` | 通常モードと初期予算(1 を参照)。`budget_used` は実行枠の開始後に `run` 内で数える |
| `run` | 実行枠。`status`(`NOT_STARTED` / `RUNNING` / `ENDED`)、`run_id`、`started_at`、`deadline`、`goal`、`release_scope`、`allowed_change_scope`、`code_state`(コミット+差分指紋)、`budget_used` |
| `baseline_snapshot` | 準備時に採取した参考の環境・コード状態。実行枠の開始時に必ず採り直す |
| `environment` / `capabilities` | 対象環境と、利用可能・不可の手段(不可なら理由) |
| `bugs[]` | Bug ID ごとの記録(2 に挙げた項目と `state`、`attempts[]`、`depends_on[]`、`retry_when`、`evidence[]`、`related_tests[]`) |
| `queue[]` | 次に処理する順に並べた Bug ID / Test ID と、その順にした理由 |
| `human_questions[]` | handoff の確認事項(最大5件)。回答と回答日時を判断記録として残す |
| `consolidation_candidates[]` | テスト統合の候補(実装しない) |

Bug ID は `BUG-0001` の形式で採番し、欠番を詰めない。

### 13.2 `qa/history.jsonl` の書式

1行1イベントの JSON。追記だけで、既存行は書き換えない。共通キーは `seq`(通し番号)、`ts`(UTC)、`type`、`run_id`(実行枠がないときは null)、`summary`。

| `type` | 追加で持つキー |
|---|---|
| `SETUP` | `refs[]` |
| `RUN_START` / `RUN_END` | `code_state`、`end_reason`(`RUN_END` のみ) |
| `TEST_RUN` | `test_id`、`kind`、`result`(PASS / FAIL / ERROR / NOT_RUN)、`code_state`、`environment`、`durations`(prepare / run / cleanup。不明は null)、`bug_ids[]`、`evidence[]`、`exit_code` |
| `FIX_ATTEMPT` | `bug_id`、`attempt`、`hypothesis`、`durations`(investigate / fix / verify)、`result`、`diff_ref`、`retry_when` |
| `EXPLORATION` | `purpose`、`code_state`、`environment`、`duration`、`operations`、`found_bug_ids[]` |
| `STATE_CHANGE` | `bug_id`、`from`、`to`、`reason` |
| `HUMAN_DECISION` | `question_id`、`answer`、`scope_confirmed` |
| `NOTE` | なし |

### 13.3 操作手順(コマンド)

コードの版は「コミットID+未コミット差分の指紋」で識別する。指紋は、追跡ファイルの差分(ステージ済みを含む)と、未追跡ファイルの内容のハッシュから作る。作業ツリーがクリーンのときは空入力の SHA-256(`e3b0c442…b855`)になる。

```bash
git rev-parse HEAD
fp(){ { git diff HEAD --binary; git ls-files --others --exclude-standard -z | sort -z | xargs -0 -r sha256sum; } | sha256sum | cut -d' ' -f1; }
fp
```

`state.json` は一時ファイルに書いて、JSON として読めることを確認してから置換する。

```bash
jq '.revision += 1 | .updated_at = (now | todate)' qa/state.json > qa/state.json.tmp \
  && jq -e . qa/state.json.tmp > /dev/null \
  && mv qa/state.json.tmp qa/state.json
```

履歴は1行ずつ検証してから追記する。

```bash
line='{"seq":2,"ts":"...","type":"NOTE","run_id":null,"summary":"..."}'
printf '%s' "$line" | jq -e . > /dev/null && printf '%s\n' "$line" >> qa/history.jsonl
```

テストの実行コマンドは `README.md` と `.github/workflows/ci.yml` の記載に従う(例: `dotnet test --project tests/Weather.Core.Tests`)。
